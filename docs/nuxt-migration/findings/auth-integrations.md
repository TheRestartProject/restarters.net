# Findings: auth-integrations

## Summary
restarters.net auth today is 100% classic Laravel session-cookie auth (guard 'web', driver 'session'), with a bolted-on legacy TokenGuard ('api' guard, driver 'token', column users.api_token) fed to the existing Vue 2 islands via an unencrypted, non-httponly cookie ('restarters_apitoken') set by EnsureAPIToken middleware after a session login. laravel/sanctum is NOT installed (composer.json/composer.lock have no sanctum/passport/socialite entries); config/cors.php exists but is generic Laravel boilerplate referencing 'sanctum/csrf-cookie' as an allowed path even though Sanctum isn't installed, and supports_credentials is false. A second, hand-rolled CORS middleware (AddCorsHeaders) sets Access-Control-Allow-Origin: * on the 'api' middleware group, which is incompatible with credentialed (cookie) cross-origin requests. Three external integrations are wired directly into Laravel's auth event lifecycle (Login/Logout/PasswordChanged Illuminate events) and depend on the server setting real HTTP cookies in the login response: Discourse SSO (spinen/laravel-discourse-sso package, GET /discourse/sso, guard 'web'+'auth', redirect-based, must stay server-side), MediaWiki silent login (LogInToWiki/LogOutOfWiki listeners set mw_* cookies directly on the Laravel response using the shared cookie domain SESSION_DOMAIN=.restarters.test), and Drip/WordPress which are pure server-to-server integrations with no user-facing auth surface. There is no email-verification flow (User does not implement MustVerifyEmail) and no OAuth/Socialite social login. Password reset is done via a custom recovery/recovery_expires token mechanism in UserController, NOT via Laravel's built-in password broker (ForgotPasswordController/ResetPasswordController exist, wired by Auth::routes(), but appear to be dead/unused code paths since routes/web.php's real reset flow is /user/recover and /user/reset).

## Key facts
- config/auth.php: guards = web (driver session, provider users/App\User) and api (driver token, provider users, hash=false — legacy Laravel TokenGuard, NOT Sanctum).
- composer.json/composer.lock: no laravel/sanctum, no laravel/passport, no laravel/socialite anywhere (grep returned empty). Only 'spinen/laravel-discourse-sso': '^2.8' relevant to auth-adjacent packages.
- app/Http/Kernel.php: 'web' group = EncryptCookies, StartSession, CheckForRepairNetwork, LanguageSwitcher, AddQueuedCookiesToResponse, ShareErrorsFromSession, VerifyCsrfToken (App\Http\Middleware\VerifyCsrfToken, custom), SubstituteBindings, LogHTTPErrorsToSentry, YesterdayBanner. 'api' group = App\Http\Middleware\AddCorsHeaders, ThrottleRequests:api, SubstituteBindings — no session/csrf middleware in api group, no Sanctum EnsureFrontendRequestsAreStateful.
- middlewareAliases include 'ensureAPIToken' => App\Http\Middleware\EnsureAPIToken and 'AcceptUserInvites' => App\Http\Middleware\AcceptUserInvites (session-based invite acceptance flow for groups/events).
- app/Http/Middleware/EnsureAPIToken.php: if Auth::check(), calls Auth::user()->ensureAPIToken() (generates 60-char random token, persists to users.api_token if absent) and sets an unencrypted, non-httponly, forever cookie 'restarters_apitoken' on the response so the Vue islands can read it via JS and send it to /api/* routes.
- resources/js/mixins/auth.js: Vue reads Vue.$cookies.get('restarters_apitoken') on component creation and stashes it in Vuex store auth/apiToken; CSRF token is passed in as a Blade-rendered prop, not fetched via API — this whole bootstrap mechanism has no server-rendering-free equivalent today.
- routes/web.php lines 44-76: Route::middleware('ensureAPIToken') wraps /user/reset, /user/recover, /user/register/{hash?}, /user/register/check-valid-email, Auth::routes() (login/logout/register/password/confirm-password — Laravel defaults), redirect('register' -> '/user/register'), GET /logout -> UserController@logout (Auth::logout() then redirect '/login').
- app/Http/Controllers/Auth/LoginController.php: uses AuthenticatesUsers trait, overrides login()/validateLogin() to add honeypot fields (my_name/my_time) and sets an 'authenticated' cookie with the email; standard sendLoginResponse() (redirect intended, or JSON if request wantsJson — Laravel default trait behavior, not overridden).
- app/Http/Controllers/Auth/RegisterController.php + Auth::routes()'s register endpoints appear DEAD CODE: create() calls undefined-in-scope 'Session::createSession($user->id)' (app/Session.php is an Eloquent model with no such static method — likely a bug never exercised) and routes/web.php redirects '/register' to '/user/register', so the real registration UI never hits this controller.
- Real registration flow: app/Http/Controllers/UserController.php getRegister()/postRegister() (routes /user/register/{hash?}), supports both new-user signup and profile completion for already-authenticated users, an optional {hash} invite parameter that links to app/Invite model (type 'group' or 'event'), geocodes city+country via App\Helpers\Geocoder, sets wiki_sync_status = WikiSyncStatus::CreateAtLogin, fires event(new UserRegistered($user)), then for brand-new users calls Auth::attempt($credentials) and redirect()->intended($redirectTo) — 'intended' URL uses Laravel session state and a custom parallel mechanism: $request->session()->get('redirectTo')/'redirectTime' set elsewhere, checked <3600s old.
- Invite acceptance: app/Http/Middleware/AcceptUserInvites.php reads session()->get('groups')/'events' (arrays of invite hashes stored server-side in session, presumably set when a guest visits an invite link before login/registration) and on next authenticated request auto-creates UserGroups/EventsUsers rows and flashes 'invites-feedback' messages to session — entirely session-cookie dependent, no token/URL-param based invite state in the API sense.
- Password reset (real flow): UserController::recover() (GET/POST /user/recover) generates a 32-byte hex 'recovery' token + recovery_expires (+24h) stored on users table, emails a link '/user/reset?recovery=...' via Notification ResetPassword; UserController::reset() (GET/POST /user/reset) validates the token+expiry, accepts password+confirm_password as plain POST fields (not Laravel's password-broker token flow), hashes and saves, fires PasswordChanged event, redirects to /login. Laravel's own ForgotPasswordController/ResetPasswordController + password_reset_tokens table (config/auth.php 'passwords') exist and are routed via Auth::routes() but are effectively unused by the real UI.
- No email verification: User model does not implement Illuminate\Contracts\Auth\MustVerifyEmail, no email_verified_at usage found, no 'verified' middleware anywhere in Kernel/routes.
- Discourse SSO: vendor/spinen/laravel-discourse-sso SsoServiceProvider registers GET {config('services.discourse.route')} = 'discourse/sso' with middleware ['web','auth'] (defaults), name 'sso.login', controller Spinen\Discourse\Controllers\SsoController@login. login() requires $request->user() (i.e. must already have a valid restarters.net session), validates Discourse's signed 'sso'/'sig' query params (config('services.discourse.secret') = env DISCOURSE_SECRET, shared secret with Discourse), builds a signed payload embedding external_id=user.id, email=user.email, name, bio=biography, then 302-redirects the browser to {DISCOURSE_URL}/session/sso_login?{query}. Pure browser-redirect flow — Discourse (talk.restarters.net) sends the user's browser to restarters.net/discourse/sso, which if unauthenticated hits Laravel's 'auth' middleware -> redirects to /login with intended URL preserved in session, user logs in, then continues to /discourse/sso, completes SSO redirect back to Discourse.
- app/Providers/EventServiceProvider.php wires: Illuminate\Auth\Events\Login -> App\Listeners\LogSuccessfulLogin (+ conditionally LogInToWiki if FEATURE__WIKI_INTEGRATION && WIKI_URL set, registered in boot()); Illuminate\Auth\Events\Logout -> App\Listeners\LogOutOfWiki; App\Events\PasswordChanged -> App\Listeners\ChangeWikiPassword; UserFollowedGroup -> AddUserToDiscourseGroup; UserConfirmedEvent/UserLeftEvent -> Add/RemoveUserFromDiscourseThreadForEvent; ApproveEvent -> CreateWordpressPostForEvent + CreateDiscourseThreadForEvent; ApproveGroup -> CreateWordpressPostForGroup + CreateDiscourseGroupForGroup. spinen package's own Listeners\LogoutDiscourseUser (ShouldQueue) also fires on Logout via its own provider wiring, sends admin API calls to Discourse to force-logout the matching Discourse user by external_id.
- MediaWiki auth sync (app/Listeners/LogInToWiki.php, LogOutOfWiki.php, ChangeWikiPassword.php): on Laravel Login event, if user.wiki_sync_status == WikiSyncStatus::CreateAtLogin, creates a MediaWiki account server-side (Addwiki\Mediawiki\Api UserCreator) using the Laravel bcrypt password hash as the MediaWiki password (comment: 'so we can log in even during a password reset'); if already Created, performs a real MediaWiki API login via Guzzle with a CookieJar, then copies every resulting MediaWiki session cookie (mw__session, mw_Token, mw_UserID, mw_UserName, prefixed by config('restarters.wiki.cookie_prefix') = env WIKI_COOKIE_PREFIX, default 'wiki_db') onto the OUTGOING LARAVEL HTTP RESPONSE via Cookie::queue(). This only works because SESSION_DOMAIN is set to a leading-dot shared domain (.restarters.test in .env.example) so the wiki.* subdomain can read cookies set by the main app. LogOutOfWiki forgets the same 4 cookies on Laravel Logout.
- Drip integration (app/DripEvent.php, class Drip facade in config/app.php): pure marketing-list sync (createOrUpdateSubscriber), triggered from backend event listeners, not from any user-facing login/registration endpoint directly — no auth coupling beyond being called during registration/consent flows server-side.
- WordPress integration (app/Listeners/Create/Edit/DeleteWordpressPost*For*.php using HieuLe\WordpressXmlrpcClient\WordpressClient): server-to-server XML-RPC publishing of approved events/groups; uses WordPress service credentials configured in config/restarters.php, entirely independent of end-user auth.
- config/cors.php: allowed_origins=['*'], supports_credentials=false, paths=['api/*','sanctum/csrf-cookie'] (leftover boilerplate — sanctum path present despite package absence). Fundamentally incompatible with any cookie-based cross-origin auth (browsers refuse credentialed requests when Access-Control-Allow-Origin is '*').
- app/Http/Middleware/AddCorsHeaders.php (custom, applied to the whole 'api' middleware group): also sets Access-Control-Allow-Origin: * and only allows methods GET, OPTIONS explicitly in its preflight branch, header allowlist Content-Type, Authorization, X-Requested-With — this is the CORS mechanism actually in effect for /api/*, not config/cors.php.
- config/session.php: driver=file (env SESSION_DRIVER), lifetime=120 min default, domain=env(SESSION_DOMAIN) (=.restarters.test locally), secure=env(SESSION_SECURE_COOKIE), http_only=true, same_site='lax'.
- routes/api.php: most GET endpoints under /api are unauthenticated (public data — homepage stats, group/event stats, group/event listings v1 and v2); a subset requires Route::middleware('auth:api') (TokenGuard) — /users/me, /users, /usersgroups/{id} DELETE (leave group, used by Vue client), v2 group-volunteer PATCH/DELETE. So today's Vue islands already call some auth-gated JSON endpoints using the api_token Bearer/query mechanism, proving the token-guard path is live, just not Sanctum.
- No socialite / OAuth / social-login providers of any kind in composer.json, User model, or routes — login is exclusively local email+password.

## Inventory
- **Login (session)**: app/Http/Controllers/Auth/LoginController.php via Auth::routes() (POST /login, GET /login). Uses Illuminate AuthenticatesUsers trait + honeypot. Sets guard 'web' session cookie. Must become: POST /api/auth/login returning either a Sanctum SPA session cookie or a token, depending on chosen strategy.
- **Logout**: GET /logout -> UserController@logout -> Auth::logout(), redirect('/login'). Fires Illuminate Logout event -> LogOutOfWiki + spinen LogoutDiscourseUser. Needs to become POST /api/auth/logout that still fires these listeners server-side.
- **Registration (real)**: UserController@getRegister/@postRegister, routes /user/register/{hash?} (GET view + POST). Handles both brand-new signup and existing-user profile completion; optional invite hash. Needs JSON API equivalents: GET config/skills+stats (public), POST /api/register (with optional invite hash), auto-login response.
- **Registration (dead/legacy)**: app/Http/Controllers/Auth/RegisterController.php + Auth::routes() register endpoints, redirected away by routes/web.php ('register' -> '/user/register'). Broken create() (undefined Session::createSession call). Recommend deleting rather than porting.
- **Email availability check**: POST /user/register/check-valid-email -> UserController@postEmail, JSON already. Trivial to keep as /api/register/check-email.
- **Password recovery request**: GET/POST /user/recover -> UserController@recover. Generates recovery/recovery_expires token, emails link. Needs POST /api/password/forgot returning JSON status.
- **Password reset completion**: GET/POST /user/reset -> UserController@reset. Validates token+expiry, sets password, fires PasswordChanged (triggers ChangeWikiPassword). Needs POST /api/password/reset (token, password, password_confirmation) as JSON.
- **Invite acceptance (groups/events)**: app/Http/Middleware/AcceptUserInvites.php, session-based (session()->get('groups')/'events'). Needs redesign: resolve invite hash directly server-side against an authenticated request rather than via session state, since SPA has no server session to stash pending invites in between an anonymous invite-link visit and a later login.
- **Discourse SSO (restarters.net as SSO provider for Discourse)**: vendor/spinen/laravel-discourse-sso, GET /discourse/sso (name 'sso.login'), middleware web+auth, config/services.php 'discourse' block (route, secret=DISCOURSE_SECRET, url=DISCOURSE_URL, user field mapping). MUST STAY SERVER-SIDE — full-page browser redirect flow initiated by Discourse, requires a live Laravel session (Auth::check()) at the time Discourse redirects the browser here.
- **Discourse logout sync**: vendor Spinen\Discourse\Listeners\LogoutDiscourseUser (ShouldQueue), fires on Illuminate Logout event, calls Discourse admin API to force-logout the corresponding Discourse user. Server-side only, no API surface needed for SPA.
- **Discourse account/group provisioning**: app/Listeners/SyncUserToDiscourse.php, AddUserToDiscourseGroup.php, CreateDiscourseGroupForGroup.php, CreateDiscourseThreadForEvent.php, Add/RemoveUserFromDiscourseThreadForEvent.php, DiscourseUserEventSubscriber.php — backend event listeners using app('discourse-client') (Guzzle, Api-Key/Api-Username headers via app/Providers/DiscourseServiceProvider.php). Pure server-to-server, no user-facing auth surface, stays server-side.
- **Discourse topic listing (public read)**: app/Http/Controllers/API/DiscourseController.php@discussionTopics, GET /api/talk/topics/{tag?}, unauthenticated, already a clean JSON API — keep as-is.
- **MediaWiki account creation + silent login**: app/Listeners/LogInToWiki.php (on Login event), creates MediaWiki account via Addwiki UserCreator using bcrypt(password) as the wiki password, then real MediaWiki API login via Guzzle CookieJar, copies mw__session/mw_Token/mw_UserID/mw_UserName cookies onto the Laravel HTTP response. MUST STAY SERVER-SIDE and MUST still execute during whatever endpoint performs login, with Set-Cookie working across the shared parent domain.
- **MediaWiki logout sync**: app/Listeners/LogOutOfWiki.php (on Logout event), forgets the 4 mw_* cookies. Server-side only, tied to whatever endpoint performs logout.
- **MediaWiki password sync**: app/Listeners/ChangeWikiPassword.php (on App\Events\PasswordChanged, fired from UserController::reset() and presumably profile password-edit). Server-side only.
- **Profile password edit**: POST /edit-password -> UserController@postProfilePasswordEdit (under auth+verifyUserConsent+ensureAPIToken group in routes/web.php around line 260-281). Needs JSON API equivalent, must still fire PasswordChanged event server-side.
- **Legacy Vue-island API token bootstrap**: app/Http/Middleware/EnsureAPIToken.php + resources/js/mixins/auth.js. Cookie 'restarters_apitoken' (forever, not httpOnly, not secure) mints/exposes users.api_token for TokenGuard-protected /api/* routes. This is the de-facto 'API auth' already in production and the most direct precedent for what a Nuxt SPA would replace with Sanctum tokens/cookies.
- **WordPress content publishing**: app/Listeners/Create/Edit/DeleteWordpressPostForEvent|Group.php via HieuLe\WordpressXmlrpcClient. Server-to-server, config/restarters.php credentials, no user auth coupling. Stays server-side, no SPA API needed.
- **Drip email marketing sync**: app/DripEvent.php createOrUpdateSubscriber, called from backend on registration/consent-change. Server-side only, no SPA API needed.
- **Social/OAuth login**: None exists. No design burden here, but note as an open question for the new SPA (is it in scope for v1?).

## Risks
- Discourse SSO redirect flow (GET /discourse/sso, guard 'web'+'auth') is fundamentally a same-browser-session, full-page-redirect handshake. If the SPA's auth strategy is Bearer-token-in-localStorage-only (no cookies), this endpoint breaks: when Discourse's browser redirect lands on restarters.net (or an api.restarters.net host) it carries no Authorization header, so Auth::check() fails and the user gets bounced to /login even though they're 'logged in' from the SPA's point of view. This forces either (a) Sanctum SPA stateful-cookie auth on a shared parent domain, or (b) a bespoke bridge (SPA redirects to a Laravel URL with a short-lived signed token/ticket in the query string that Laravel exchanges for a session before continuing the Discourse SSO dance).
- MediaWiki silent login/logout depends on Laravel's HTTP response being able to Set-Cookie for a *different* subdomain (wiki.restarters.net) via a shared parent domain (SESSION_DOMAIN=.restarters.test pattern). This still works if app/api/wiki all share one parent domain with cookies Domain=.restarters.net + SameSite=None/Secure — but any origin split beyond a shared parent domain (e.g. a separate marketing/CDN domain, or the Capacitor mobile app which has no browser cookie jar shared with a website at all) breaks it completely. Mobile app users would get no MediaWiki SSO at all under the current mechanism.
- Intended-URL handling after login (redirect()->intended(), plus a parallel custom session('redirectTo')/'redirectTime' mechanism in UserController::postRegister) is pure server-side session state. An SPA has no equivalent 'session' to stash the pre-login destination in on the server; this logic must move entirely to client-side routing (Nuxt route guard remembers intended route, redirects post-login) — anything currently relying on Laravel computing the redirect target server-side (e.g. links directly into /discourse/sso that trigger a login detour) needs re-design.
- AcceptUserInvites middleware stores pending group/event invite hashes in the PHP session between an anonymous visit to an invite link and a later authenticated request. This session-bridging pattern has no direct SPA equivalent (no shared server session across an anonymous and later authenticated browser tab in a token-auth world) — needs redesign, e.g. invite hash carried in the register/login API payload directly, or a short-lived DB-backed pending-invite record keyed by hash + resolved at accept-time regardless of session.
- Current CORS config is incompatible with credentialed cross-origin requests: config/cors.php has supports_credentials=false and allowed_origins=['*']; the actually-active AddCorsHeaders middleware also hardcodes Access-Control-Allow-Origin: '*'. Browsers reject 'Access-Control-Allow-Origin: *' combined with 'credentials: include' fetches, so if the Nuxt SPA lives on a different origin from the API and needs cookie-based (Sanctum SPA) auth, this CORS config must be rewritten to an explicit allowed-origins list + supports_credentials=true, with Access-Control-Allow-Credentials: true and a specific (non-wildcard) Access-Control-Allow-Origin echoed per-request.
- Password reset today bypasses Laravel's password-broker/token table entirely (custom recovery/recovery_expires columns on users, plain-text token in a query string, 24h expiry, no visible rate-limit beyond the honeypot on login/register). Porting this to an API needs either keeping the bespoke mechanism (fine, just needs JSON endpoints) or migrating to Laravel's password broker — either way it's a real endpoint to design (POST /api/password/forgot, POST /api/password/reset), independent of the Sanctum/session choice.
- No email verification exists today (MustVerifyEmail not implemented) — if the SPA migration is used as an opportunity to add it, that's new scope, not a port; flag to the design so it isn't silently assumed to already exist.
- The existing api_token (TokenGuard) cookie 'restarters_apitoken' is set without httpOnly or secure flags specifically so client JS can read it — this is a real, already-shipped precedent for a non-Sanctum bearer-token pattern, but it's also a live XSS exposure (a stolen non-expiring token = permanent account takeover, since ensureAPIToken() tokens are 'forever' cookies with no rotation/revocation UI found). Any new design should not simply carry this forward unmodified.
- Future Capacitor mobile app cannot use browser cookies for auth the way a website can (no shared cookie jar with restarters.net domain in the way a WebView-less native shell needs), so a pure Sanctum-SPA-cookie-only strategy would need a parallel token-based path anyway for mobile — meaning the API will likely need to support both mechanisms unless everything routes through a Capacitor WebView (out of scope per the task, but the auth API shape should not preclude it).

## Recommendations
- Adopt Laravel Sanctum's SPA 'stateful' cookie authentication as the primary browser-based auth mechanism (install laravel/sanctum, add EnsureFrontendRequestsAreStateful to the api middleware group ahead of the auth guard, configure sanctum.stateful with the Nuxt dev/prod hostnames, set SESSION_DOMAIN to a shared parent domain e.g. .restarters.net covering app./api./wiki./talk. subdomains, same_site=lax or none+secure as required for the chosen subdomain topology). This preserves the exact mechanism Discourse SSO and MediaWiki silent-login already depend on (a real Laravel session + Set-Cookie on same/sibling-domain requests), so those two integrations need zero redesign beyond CORS/cookie config, only a login endpoint change (GET /sanctum/csrf-cookie then POST /api/login with credentials:'include').
- In parallel, expose a token-based auth path (Sanctum personal access tokens — Sanctum's non-SPA 'API token' mode: POST /api/login returns a bearer token for non-browser/native clients) reserved for the future Capacitor app — Capacitor's WebView can still be pointed at the stateful cookie flow if it shares the app's origin via a custom scheme + cookie jar (check /home/edward/FreegleDockerWSL/iznik-nuxt3 for Freegle's precedent), but a fallback bearer-token mode removes that dependency and should be designed in from day one even if unused initially, matching the task's 'keep it possible' constraint.
- Retire the ad-hoc EnsureAPIToken/'restarters_apitoken' cookie + TokenGuard('api', driver 'token') mechanism entirely once Sanctum is in place — it's a strict subset of what Sanctum provides (revocable, expiring, abilities-scoped tokens vs a single forever un-rotatable token per user) and its /api routes already gate on 'auth:api' so the guard swap is mechanical (change config/auth.php 'api' guard driver to 'sanctum').
- Rewrite config/cors.php to an explicit allowed_origins list (Nuxt dev http://localhost:3000-ish + production app domain), supports_credentials=true, and delete/replace the custom AddCorsHeaders middleware (its Access-Control-Allow-Origin:'*' will otherwise silently defeat Sanctum cookie auth for any cross-origin deployment) — or keep app+api same-origin (reverse-proxied) to sidestep CORS/third-party-cookie issues altogether, which is the simplest and most Safari/Chrome-ITP-resilient option and is likely how Discourse/MediaWiki cookie sharing already works.
- Keep GET /discourse/sso (spinen package) mounted on the Laravel app unchanged, guarded by session auth; if app.restarters.net (Nuxt) and the Laravel API end up on different subdomains, verify the browser still holds a valid Sanctum session cookie scoped to the shared parent domain when Discourse redirects there — test this specific cross-subdomain hop explicitly since it's the highest-risk integration point in the whole migration.
- Design explicit JSON endpoints mirroring the real (non-dead-code) flows only: POST /api/auth/login, POST /api/auth/logout, POST /api/auth/register (folding in optional invite hash + the existing-user 'complete profile' variant as a separate endpoint rather than overloading one), POST /api/auth/password/forgot, POST /api/auth/password/reset, GET /api/auth/email-available. Do not port app/Http/Controllers/Auth/RegisterController.php or ForgotPasswordController/ResetPasswordController — they're dead code; delete them during the migration rather than translate them.
- Redesign invite acceptance as a stateless flow: resolve the invite hash server-side against the Invite model directly inside the register/login API call (pass hash as a request field) instead of relying on PHP session state bridging an anonymous visit and a later authenticated action — this removes the AcceptUserInvites session-array pattern entirely and is more robust for an SPA (no dependency on hitting the exact same server session across page loads).
- Add MustVerifyEmail / email verification as a deliberate, separately-scoped decision for the new API (it doesn't exist today) rather than assuming parity — flag to product/design owner.
- For the api_token/TokenGuard-authenticated existing endpoints in routes/api.php (/users/me, /users, /usersgroups/{id}, v2 volunteer PATCH/DELETE), plan a like-for-like swap to Sanctum tokens/cookies with no route-shape changes — these are already clean JSON APIs and the auth-guard change is the only work needed.
