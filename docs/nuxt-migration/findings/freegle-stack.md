- **API client: BaseAPI class pattern**: api/BaseAPI.js (400 lines) — a plain ES class (not $fetch/useFetch; comment explains $fetch/useFetch break on Node 18, so raw fetch() wrapped in a custom fetchRetry() from composables/useFetchRetry.js is used instead). Constructor takes `config` (the Nuxt runtimeConfig). Exposes $getv2/$postv2/$patchv2/$putv2/$postFormv2/$delv2 helper methods, all funneling into $requestv2(method, path, config, logError, body). Base URL comes from `this.config.public.APIv2` (runtimeConfig.public.APIv2, itself sourced from config.js/env var IZNIK_API_V2). Auth: reads useAuthStore() for JWT (Authorization header) and 'persistent' token (Authorization2 header fallback); appends `loggedInAs=<id>` query param when impersonating, and a monotonic `requestid=` counter for every call. On 2xx, returns parsed data; server can piggyback fresh JWT/persistent tokens in the response body which get written back via authStore.setAuth(). Non-2xx throws typed APIError (api/APIErrors.js) carrying {request:{path,method,headers,params,data}, response:{status,data}}. 401 handling is selective: only /session responses force a logout (clear auth); any other endpoint's 401 leaves the session intact (documented regression fix for over-aggressive logout). Errors are conditionally reported to Sentry via a `logError` param that can be boolean OR a function of the response data (e.g. UserAPI.fetchMT suppresses Sentry for expected 404s). A module-level `globalAbortController` (with enterLogoutMode/exitLogoutMode/abortAllPendingRequests exports) lets the auth store cancel every in-flight request atomically on logout to stop stale responses re-establishing session cookies.
- **Per-domain API classes extend BaseAPI**: api/*.js — one file per REST resource (UserAPI.js, GroupAPI.js, ChatAPI.js, MessageAPI.js, SessionAPI.js, ... 47 files total, api/BaseAPI.js is the shared parent, api/APIErrors.js the error types). Each class method is a thin wrapper calling this.$getv2/$postv2/etc with a hardcoded REST path, e.g. UserAPI.fetch(id) -> this.$getv2('/user/'+id); UserAPI.save(event) -> this.$patchv2('/user', event); UserAPI.signUp(params) -> this.$putv2('/user', params). Domain-specific validation lives here too (e.g. throws TypeError for NaN ids) rather than in BaseAPI.

## Risks
- The Freegle stack keeps SSR partially enabled (routeRules per path) rather than pure SPA — if the new restarters.net Nuxt client is meant to be a pure SPA (per the task's 'completely separate Nuxt 4 SPA client' framing), the routeRules/ISR/prerender machinery here is more complexity than needed; blindly copying it would import unnecessary SSR/Nitro concerns.
- bootstrap-vue-next + Bootstrap 5 explicitly lack SSR support per Freegle's own comments — if restarters.net wants any SSR/prerendering later, bootstrap-vue-next remains a blocker exactly as it is for Freegle.
- Freegle's vue/pinia versions are hard-pinned via package.json `overrides` due to known compatibility breakage ('comment7': may need fixed vue@3.5.13 @pinia/nuxt@0.9.0 pinia@2.3.1 pinia-plugin-persistedstate@4.2.0) — a fresh Nuxt 4 setup should not assume current latest versions of these packages interoperate cleanly; expect to pin similarly and verify.
- No route-middleware-based auth guard exists to copy — the per-page forceLogin/modal pattern is Freegle-specific UX (never redirect, always show inline CTA + modal). This is a design choice, not an incidental gap; the new app's PRD should explicitly decide whether to replicate this UX or use conventional Nuxt route middleware (which Freegle deliberately avoids).
- api/index.js being a generated file (via api/index.generate.js) is a convention that must be replicated deliberately (a generator script) or consciously dropped in favor of manual/auto-import wiring — otherwise risk of drift between the exported api object and the actual API class files.
- Capacitor readiness in Freegle relies on config.ISAPP branching scattered across nuxt.config.ts, capacitor.config.ts, and stores/mobile.js — this is diffuse, not centralized; replicating 'capacitor-ready' for restarters.net will require deciding early where this flag lives and threading it consistently, since Freegle shows it touches SSR flag, asset compression, import-map feature, ad/consent scripts, and login provider selection all independently.

## Recommendations
- For restarters.net's Nuxt 4 client, adopt BaseAPI's class-per-resource pattern (api/BaseAPI.js + api/<Resource>API.js + generated api/index.js factory) exactly — it cleanly maps Laravel's API-only controllers to typed JS client methods and centralizes auth-header injection, retry, and error typing in one place.
- Decide explicitly whether restarters.net wants Freegle's hybrid SSR-with-per-route-ssr:false, or true ssr:false everywhere (simpler, matches the task's 'SPA client' framing more directly) — recommend the latter given restarters.net has no equivalent ad/SEO-crawler-preview requirement driving Freegle's hybrid approach, unless SEO for public group/event pages is a stated requirement.
- If any SSR is wanted for SEO on public pages (e.g. public group directory pages), do not use bootstrap-vue-next/Bootstrap in those SSR'd routes' component trees, mirroring Freegle's <client-only> wrapping strategy — otherwise plan for pure ssr:false and skip this complexity entirely.
- Replicate the auth store's localStorage-only token persistence (JWT + refresh/persistent token via pinia-plugin-persistedstate `pick` allowlist) rather than persisting the whole user object or using cookies, to keep the design Capacitor-compatible from day one (Capacitor WebViews handle localStorage more predictably than SSR cookies).
- For Capacitor-readiness, centralize a single `IS_APP` runtime flag (env-driven, exposed via runtimeConfig.public) from the start, and route ssr-disable/asset/import-map/login-provider decisions through it, rather than letting the concern spread implicitly.
- Adopt the vitest.config.mts pattern of a hand-built alias map + happy-dom + setupFiles global polyfills only if targeting components/composables/stores in isolation without full Nuxt context; confirm whether restarters.net prefers this lighter/faster approach vs. @nuxt/test-utils' Nuxt-aware test environment — Freegle chose the former for speed/memory reasons specific to their WSL CI, which may or may not apply.
- Explicitly design the auth-gating UX (redirect vs. modal-overlay-without-redirect) rather than defaulting to Freegle's no-middleware/forceLogin-modal convention, since that is a deliberate Freegle product decision, not a Nuxt/Vue best practice — restarters.net may prefer standard Nuxt route middleware (definePageMeta({ middleware: 'auth' })) for simplicity.
