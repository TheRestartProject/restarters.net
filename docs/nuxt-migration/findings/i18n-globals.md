# Findings: i18n-globals

## Summary
Restarters.net's i18n today is a hybrid: Laravel lang/*.php (27 files x en, mirrored for fr/fr-BE + 9 other stub locales, plus lang/*.json for device-category names) is compiled at Vite build time into a single VITE_LARAVEL_TRANSLATIONS global via a custom-patched vite-plugin-laravel-translations wrapper (vite.config.js:37-76), consumed client-side by a Vue 2 mixin (resources/js/mixins/lang.js + lang-utils.js) that reads the active locale off document.documentElement.lang (itself set server-side from app()->getLocale() in the Blade layout). Pluralization uses Laravel's own singular|plural / {n} / [n,m] syntax, reimplemented faithfully in JS. Separately, server-injected context is pervasive and unconsolidated: CSRF meta tag, window.restarters (cookie/analytics flags), several raw env() calls inlined directly in Blade (GOOGLE_TAG_MANAGER_ID, SESSION_DOMAIN, DISCOURSE_URL, APP_SHOW_BRANCH, APP_SHOW_COMMUNITY_TEST), Auth::user() fields read ad hoc throughout navbar.blade.php, PHP-session-held locale and column_preferences, and — most significantly — every major page (events, groups, dashboard, fixometer, networks) bootstraps its root Vue component via @json/json_encode-encoded HTML attributes rather than an API call. No consolidated bootstrap/session API endpoint exists today (closest is an unused GET /api/v2/users/me); app/Http/Middleware/APISetLocale.php already provides a stateless per-request locale override suitable for reuse in the API-only future.

## Key facts
- lang/ directory (lang/*.php + lang/*.json + per-locale dirs) has 12 locales: de, en, es, fr, fr-BE, it, ne, nl, nl-BE, no (+ their .json siblings for top-level device-category-name keys); only en, fr, fr-BE are noted as needing translation completeness per user instruction.
- lang/en/ has 27 PHP files (grouped by domain: admin, auth, brands, calendars, category, countries, dashboard, device-audits, devices, discourse, event-audits, events, general, group-audits, group-tags, groups, landing, login, networks, notifications, onboarding, partials, passwords, profile, registration, reporting, skills, ...). lang/fr and lang/fr-BE mirror the same file set with translated values (lang/fr/general.php confirmed present and populated).
- Blade consumes lang/*.php via standard Laravel @lang('file.key') directive (e.g. resources/views/layouts/app.blade.php:21 @lang('onboarding.slide1_heading')) and __('file.key') function calls (resources/views/layouts/header_plain.blade.php:45 __('landing.intro') in a meta description tag). 80 files under resources/views match @lang(/{{ __( patterns.
- JS translation pipeline: vite.config.js defines a custom laravelTranslationsWithJson() plugin (vite.config.js:56-76) wrapping vite-plugin-laravel-translations@0.3.1. It reads all lang/*.php via the base plugin into a `define` global VITE_LARAVEL_TRANSLATIONS map keyed by locale, then also deep-merges each lang/<locale>.json file's top-level keys (device category/cluster names) into the same per-locale object — done manually because the plugin's own includeJson option is broken on Node 18+ (double-path + missing JSON import attribute bug, documented inline vite.config.js:37-43). Hot-reload: any lang/*.php or *.json change triggers a full Vite server restart (handleHotUpdate, vite.config.js:72-74).
- Client-side translation consumption: import.meta.env.VITE_LARAVEL_TRANSLATIONS is read once in resources/js/mixins/lang.js:4 into `translations`. Locale is resolved from document.documentElement.lang (resources/js/mixins/lang.js:6-8), NOT from a Vuex store or prop — i.e. it reads the server-rendered <html lang> attribute set by app()->getLocale() in resources/views/layouts/header.blade.php:2.
- resources/js/mixins/lang.js exports a Vue 2 mixin (default export) that injects `this.$lang = {get, choice, getLocale}` in beforeCreate() and adds a `__(key, values)` instance method used throughout templates like Blade's helper; falls back to Sentry.captureMessage('Missing translation ...') and returns the raw key on error.
- Actual interpolation/pluralization logic lives in resources/js/mixins/lang-utils.js (pure functions translateWithLocale/choiceWithLocale, no Vite/Sentry deps, designed to be unit-testable) — reimplements Laravel's :param substitution (regex /:(\w+)/g) and pluralization syntax including plain 'singular|plural' (count===1 => first segment else last), '{n} text' exact-match segments, and '[n,m]'/'[n,*]' range segments, mirroring Laravel's trans_choice() PHP semantics.
- PHP lang files use Laravel's native pluralization conventions: pipe-separated 'singular|plural' (e.g. lang/en/dashboard.php:40 'newly_added' => 'Newly added: :count group...|Newly added: :count groups...'), and ICU-ish range/exact syntax e.g. lang/en/networks.php:17-18 "'groups' => '{1} Group|[0,*] Groups'". Parameters use Laravel's `:param` placeholder convention (e.g. :count, :value) substituted by str_replace-style regex both server (Laravel trans()) and client (lang-utils.js) side.
- Locale determination/switching server-side: config/app.php 'locale' => 'en', 'fallback_locale' => 'en'. GET /set-lang/{locale} route (routes/web.php:458) -> App\Http\Controllers\LocaleController::setLang() sets session('locale'), App::setLocale(), LaravelLocalization::setLocale(), and persists to Auth::user()->language if logged in, then redirects back (full page reload pattern, not SPA-friendly). app/Http/Middleware/CheckForRepairNetwork.php:59-69 also auto-sets locale from a Network's default_language on first visit if no session locale exists yet. app/Http/Middleware/APISetLocale.php lets an API request set the request-scoped locale via a `?locale=` query/body param (app()->setLocale($locale)) without persisting it — usable pattern for a stateless API.
- No dedicated 'bootstrap'/'session'/'me+config' API endpoint currently exists. routes/api.php has GET /users/me (API\ApiController::getUserInfo, explicitly commented 'Not used but worth keeping and tested') and GET /users (getUserList) but nothing that returns combined user+config+translations+feature-flags for SPA bootstrap.
- Vue mounting today is imperative/non-SPA: resources/js/app.js:393-397 does `window.jQuery('.vue').each(...)` and does `new Vue({el, ...})` per DOM node carrying a `.vue` class, receiving its initial state via Blade-rendered HTML attributes (kebab-case props) as itemized in inventory — this whole per-page prop-passing pattern disappears in the Nuxt SPA and must be replaced by page-specific GET API endpoints.
- Feature/env flags currently only surfaced via raw env() calls directly in Blade (GOOGLE_TAG_MANAGER_ID, SESSION_DOMAIN, APP_SHOW_BRANCH, APP_SHOW_COMMUNITY_TEST, DISCOURSE_URL) — none of these are exposed through a config API; Laravel's config() layer is barely used in views (grep found no config('services.xxx') style map/feature-flag calls in the checked layout files), meaning a new config-serving endpoint has to be built rather than adapted from an existing pattern.
- No Google Maps or Mapbox key is exposed to the frontend: maps use Leaflet with free OSM/CARTO raster tiles (resources/js/constants.js: LEAFLET_TILES = 'https://{s}.basemaps.cartocdn.com/...', LEAFLET_ATTRIBUTION) — confirms per project memory that geocoding is server-side only (Google Geocoder is called from Laravel, not exposed as a client API key).

## Inventory
- **window.restarters (cookie_domain, analyticsCookieEnabled)**: resources/views/layouts/header.blade.php:49-54 and header_plain.blade.php:64-70. restarters.cookie_domain = env('SESSION_DOMAIN'); restarters.analyticsCookieEnabled computed from js-cookie 'gdprcookienotice' cookie. Consumed in resources/js/app.js (window.restarters.analyticsCookieEnabled, line ~277) to decide whether to load Matomo.
- **CSRF meta tag**: <meta name="csrf-token" content="{{ csrf_token() }}"> in resources/views/layouts/header.blade.php:9 and header_plain.blade.php:9. Read by resources/js/bootstrap.js:19 (sets axios default header) and resources/js/app.js:356 and resources/js/components/EventInviteModal.vue:208 (manual $.ajax / fetch header). Irrelevant for a token/Bearer-auth SPA API; would be replaced by Sanctum/JWT auth headers.
- **app()->getLocale() -> <html lang>**: resources/views/layouts/header.blade.php:2 `<html lang="{{ app()->getLocale() }}">`. Read client-side by resources/js/mixins/lang.js:7 `document.documentElement.lang` as the active locale for the __() helper — this is literally how Vue components learn the current locale today.
- **GOOGLE_TAG_MANAGER_ID (server env, inlined)**: resources/views/layouts/header.blade.php:80 and header_plain.blade.php:96, `env('GOOGLE_TAG_MANAGER_ID')` inlined directly into a <noscript><iframe src=...> — a raw env() call in a Blade view (anti-pattern but present).
- **SESSION_DOMAIN (server env, inlined)**: resources/views/layouts/header.blade.php:50, header_plain.blade.php equivalent — env('SESSION_DOMAIN') inlined into window.restarters.cookie_domain.
- **APP_SHOW_BRANCH / FLY_APP_NAME / MAILPIT_URL branch banner**: resources/views/layouts/navbar.blade.php:15-38. Dev/PR-preview only: shows a fixed banner with the Fly branch name and a Mailpit link, computed server-side (env() + git branch shell-out) and echoed into the DOM.
- **APP_SHOW_COMMUNITY_TEST flag**: resources/views/layouts/navbar.blade.php:40-48. Injects a <style> watermark background when env flag set; purely presentational env-gated flag.
- **Auth::user() object fields scattered through navbar**: resources/views/layouts/navbar.blade.php:93 `$user = Auth::user()`, then id/name/username/profile-picture-path/roles/networks are read directly via Blade (lines 100-151), e.g. `Notifications :user-id="{{{ Auth::user()->id }}}" discourse-user-name="{{{ Auth::user()->username }}}"`, role checks via App\Helpers\Fixometer::hasRole(Auth::user(), 'Administrator'/'Host'/'NetworkCoordinator'), and Auth::user()->networks. This is the main 'current user' server injection point — no single serialized user object, individual fields spread through the template and passed as separate Vue props.
- **DISCOURSE_URL (server env, inlined)**: resources/views/layouts/navbar.blade.php:59-60 and 100, used both for building an SSO link href and passed as a Vue prop `discourse-base-url` to the Notifications component.
- **session('column_preferences')**: resources/views/group/index.blade.php:74, `$user_preferences = session('column_preferences')` — a UI-state preference stored server-side in the PHP session and read into Blade to configure a table's visible columns.
- **session('locale')**: app/Http/Middleware/CheckForRepairNetwork.php:59-69 and app/Http/Controllers/LocaleController.php — locale is stored in the PHP session (and persisted to Auth::user()->language when logged in) and read by App::setLocale()/LaravelLocalization::setLocale() on every request. Route: GET /set-lang/{locale} (routes/web.php:458).
- **Flash/validation messages via session**: Standard Laravel `session('success')`, `$errors` bag etc., consumed with `@if(session(...))` across many views (resources/views/{group,events,category,auth,skills,tags,role,brands,admin,user,faultcat}/*.blade.php — 19+ files matched by grep for `session(`). No single injection point; each view/controller pushes its own flash key via `->with(...)` in redirect responses.
- **Blade @json/json_encode props into Vue root components (per-page bootstrap data)**: Every top-level page passes its initial data as encoded HTML attributes to a root Vue component mounted via `.vue` class + `window.jQuery(".vue").each(...)` in resources/js/app.js:393-397. Examples: resources/views/events/index.blade.php:87-108 (initial-events, canedit, idgroups, initial-group); resources/views/events/create.blade.php:25-32 (duplicate-from, groups, can-approve, create-group); resources/views/events/view.blade.php:112-122 (devices, initial-event, is-attending, canedit, candelete, is-admin, in-group, hosts, calendar-links); resources/views/events/edit.blade.php:62-68; resources/views/group/index.blade.php:51-70 (your-groups, nearby-groups, can-create, network, networks, all-group-tags, show-tags); resources/views/group/view.blade.php:145-154 (initial-group, group-stats, device-stats, cluster-stats, top-devices, events, canedit, candemote, can-see-delete); resources/views/networks/show.blade.php:27-32 (network, initial-stats, initial-tags, can-manage-tags, can-associate-groups, is-logged-in); resources/views/dashboard/index.blade.php:49-55 (your-groups, nearby-groups, upcoming-events, is-logged-in, new-groups); resources/views/fixometer/index.blade.php:19-25 (latest-data, impact-data, clusters, brands, barrier-list, is-admin, user-groups); resources/views/category/index.blade.php:38 and role/all.blade.php:33 (tableData). All of this must move to API calls (GET endpoints per page/resource) in the Nuxt migration — none of it is currently exposed as a general-purpose API.
- **Onboarding modal content and $onboarding flag**: resources/views/layouts/app.blade.php:21-45 injects onboarding.* translated strings directly into a Bootstrap modal server-side via @lang(), and header.blade.php:74 checks `isset($onboarding) && $onboarding` to add an 'onboarding' body class — server-side conditional UI state.

## Risks
- 9 of 12 lang locales (de, es, it, ne, nl, nl-BE, no) are stub/unmaintained per user instruction (only en/fr/fr-BE matter) — if the JSON-export build step blindly emits all locale files, the Nuxt locale switcher UI must be scoped to only en/fr/fr-BE or it will expose incomplete/stale translations as selectable options.
- vite-plugin-laravel-translations@0.3.1's broken includeJson option (worked around manually in vite.config.js:37-43) is unmaintained upstream risk — the Nuxt migration should not carry this dependency forward; the recommended custom JSON-export script removes the dependency entirely, which should be treated as a required change, not optional cleanup.
- No existing API contract for user+config bootstrap data means the GET /api/v2/session endpoint is net-new design surface with no precedent to copy from this codebase (unlike other API endpoints that mirror existing Blade prop shapes) — higher risk of under-scoping fields that later turn out to be needed (e.g. column_preferences, onboarding_seen state) causing follow-up endpoint churn.
- APP_SHOW_BRANCH banner logic does a live `exec('cd ...; git branch | grep...')` shell-out in navbar.blade.php when FLY_APP_NAME is absent (local dev fallback) — porting this into an API endpoint means either keeping a shell-out in an API controller (security/perf smell) or dropping local-dev branch detection fidelity; flag for explicit decision rather than silent behavior change.
- CSRF/session-cookie removal changes the auth model fundamentally (meta-tag CSRF + PHP session today) — if Sanctum SPA cookie auth is chosen instead of Bearer tokens for expedience, it will need revisiting when the Capacitor app is built later (cookie auth does not extend to a Capacitor WebView cleanly per the recommendation above), so this decision should explicitly be locked in now rather than deferred, since it is genuinely difficult to change once many API consumers depend on it.

## Recommendations
- i18n mechanism for Nuxt: use @nuxtjs/i18n (v9, Nuxt 4 / Vue 3 compatible) rather than hand-rolled vue-i18n wiring, since it gives SSR-safe (even though this is an SPA) locale routing, persisted locale cookie, and lazy-loaded locale JSON out of the box — closer to Freegle's iznik-nuxt3 conventions if Freegle already uses it (verify against scout-freegle's findings) than reinventing resources/js/mixins/lang.js's manual document.documentElement.lang read.
- Keep lang/*.php (and lang/*.json for category names) in Laravel as the single source of truth — do NOT fork translations into a separately maintained Nuxt-side file, since PHP-side validation strings, emails, and any server-rendered content (transactional emails, PDF/CSV exports) still need Laravel's own trans()/trans_choice(). Build a compile step (artisan command or a small Node script) that walks lang/<locale>/*.php via `php -r` (or artisan tinker) and lang/<locale>.json, and emits public JSON per locale (e.g. lang/compiled/en.json) at build/deploy time — this is the natural successor to vite.config.js's laravelTranslationsWithJson() plugin, just targeting flat JSON files consumed by @nuxtjs/i18n's lazy() loader instead of a Vite `define` global.
- Preserve the existing pluralization syntax verbatim (singular|plural, {n} exact, [n,m]/[n,*] range) — vue-i18n's own pluralization has different rule syntax, so either (a) keep using a ported version of resources/js/mixins/lang-utils.js's translateWithLocale/choiceWithLocale as a custom messageResolver/pluralRules for @nuxtjs/i18n, or (b) write a one-time migration script converting all lang/*.php pipe/range syntax into ICU MessageFormat plural syntax during the JSON export step. Recommend (a): minimal risk, reuses already-tested logic (resources/js/mixins/lang-utils.js is written to be unit-testable independent of Vite), avoids relying on translators to have written ICU-correct strings for 12 locales.
- Locale switching + persistence: replace GET /set-lang/{locale} (full-page redirect) with a stateless pattern — Nuxt sets locale client-side (e.g. via @nuxtjs/i18n's own cookie, key e.g. 'restarters_locale') and passes `?locale=` or an `Accept-Language`/custom header on every API call so Laravel's existing app/Http/Middleware/APISetLocale.php (already built for exactly this, currently used for read-only concerns like translated country names) governs server-rendered translated content (e.g. transactional email subject/body, PDF exports). When the user is logged in, PATCH the persisted locale to their profile via a small dedicated endpoint (e.g. PATCH /api/v2/session {locale}) mirroring what LocaleController::setLang currently does inline, rather than reusing the old redirect route.
- API shape for bootstrap/session context: add GET /api/v2/session (or /api/v2/bootstrap) returning a single payload consumed once on app init and cached in a Pinia store: { user: {id, name, username, email, avatar_url, roles: [...], networks: [...], language} | null, config: { discourse_url, discourse_sso_url, google_tag_manager_id, session_domain, matomo_site_id, mailpit_url, show_branch_banner: bool, branch_label, show_community_test_banner: bool }, flags: { app_show_branch, app_show_community_test, onboarding_seen: bool } }. This single call replaces: navbar.blade.php's scattered Auth::user() field reads, the env()-inlined GTM/session-domain/Discourse URLs, and the APP_SHOW_BRANCH/APP_SHOW_COMMUNITY_TEST env flags currently computed inline in Blade with a git-branch shell-out (move that branch-derivation logic server-side into the endpoint, not the SPA).
- For CSRF: since the Nuxt app is a separate SPA calling an API-only Laravel backend, drop the meta-tag CSRF pattern entirely (resources/js/bootstrap.js:19, app.js:356, EventInviteModal.vue:208 all disappear) in favor of Laravel Sanctum SPA cookie-based auth (if same top-level domain, matches the Freegle iznik-nuxt3 approach — verify) or a token/Bearer auth flow if cross-domain/Capacitor mobile is the long-term target; Bearer/token auth is preferable given the stated future Capacitor mobile app requirement, since cookie-based SPA auth doesn't extend cleanly to a Capacitor WebView.
- Convert every per-page @json/json_encode Blade prop block (see inventory item on Blade props) into a corresponding REST/JSON API endpoint under routes/api.php — e.g. events/index.blade.php's initial-events/canedit/idgroups/initial-group props become GET /api/v2/groups/{id}/events; group/view.blade.php's initial-group/group-stats/device-stats/cluster-stats/top-devices/events props become GET /api/v2/groups/{id} (+ nested stats sub-resources or query params); dashboard/index.blade.php's your-groups/nearby-groups/upcoming-events/new-groups become GET /api/v2/dashboard. Audit each of the 17 files flagged by the @json/json_encode grep individually before the Nuxt page is built, since several (categories-table, roles-table) are simple list endpoints while others (fixometer/index.blade.php) aggregate multiple independent data sources that should probably become separate parallel API calls rather than one giant endpoint.
- Move flash/validation messaging off PHP session entirely: API error responses should return standard Laravel validation JSON (422 + errors bag, already how Laravel APIs work) and success messages should be encoded in the API response body (e.g. {message: 'Group updated'}) for the Nuxt store to surface as a toast, rather than relying on session('success') read via @if(session(...)) in Blade.
- Migrate `session('column_preferences')` (group/index.blade.php:74) to a user-preferences API resource (e.g. part of the GET /api/v2/session payload's user object, or a dedicated GET/PUT /api/v2/users/me/preferences) so column visibility state survives login across devices, matching the Pinia-store-hydrated-from-API pattern used elsewhere.
