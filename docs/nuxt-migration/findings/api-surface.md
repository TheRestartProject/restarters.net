# Findings: api-surface

## Summary
restarters.net exposes a two-tier JSON API: an unversioned legacy tier (app/Http/Controllers/ApiController.php, OutboundController.php, and non-v2 methods in app/Http/Controllers/API/*.php, routed at the top of routes/api.php) used by Zapier/TRP.org/RepairTogether/the current Vue islands, and a newer, OpenAPI-documented, resource-based v2 tier (Route::prefix('v2') in routes/api.php, all methods suffixed v2) covering Groups, Events, Devices, Networks, Alerts, Items with fairly complete CRUD for Groups/Events/Devices and read-heavy coverage for Networks. Auth is Laravel's built-in TokenGuard against a users.api_token column (config/auth.php 'api' guard, driver 'token') - critically, there is NO API endpoint that issues this token; it is minted lazily by app/User.php::ensureAPIToken() and handed to the browser as a cookie only as a side-effect of a full session-based Blade login (app/Http/Middleware/EnsureAPIToken.php on routes/web.php groups), which is the single largest gap for a decoupled Nuxt SPA. Huge functional areas remain entirely Blade-only with zero JSON contract: registration/password-reset, user profile/preferences editing, event/group self-join RSVP, image/photo uploads, dashboard aggregate data, admin CRUD (categories/brands/skills/roles/global tags), maps autocomplete proxy, and most of Discourse beyond a read-only topic list.

## Key facts
- routes/api.php has 133 lines; a legacy flat set of endpoints (lines 1-70, no version prefix) plus a versioned block under Route::prefix('v2') (lines 72-134) wrapped in App\Http\Middleware\APISetLocale middleware.
- Controllers live in app/Http/Controllers/API/ (namespace App\Http\Controllers\API): AlertController(290 lines), DeviceController(614), DiscourseController(38), EventController(759), GroupController(1299), ItemController(67), NetworkController(823), UserController(137), UserGroupsController(124). Plus non-namespaced app/Http/Controllers/ApiController.php(311) and OutboundController.php(141) hold the legacy/unversioned endpoints.
- AUTH MECHANISM: config/auth.php guard 'api' => driver 'token', provider 'users', hash=false. This is Laravel's built-in TokenGuard (not Sanctum/Passport - composer.json has neither package). TokenGuard resolves a user by matching the 'api_token' column on the users table against a value it looks for, in order, in: request input field 'api_token' (query string or POST body), or the Authorization: Bearer <token> header.
- TOKEN ISSUANCE IS NOT AN API ENDPOINT. app/User.php:ensureAPIToken() lazily generates+persists a 60-char random api_token column value the FIRST time it's called, but nothing in api.php ever calls it. It's invoked exclusively by app/Http/Middleware/EnsureAPIToken.php (aliased 'ensureAPIToken' in Kernel.php), attached to web.php route groups (session-authenticated Blade pages only, e.g. lines 46, 260, 429 of routes/web.php). On any authenticated Blade page load, that middleware ensures the user has an api_token and returns it via a plaintext, non-httponly cookie 'restarters_apitoken' (see EnsureAPIToken.php line 27) so the embedded Vue islands can read it client-side and attach it to API calls. THERE IS NO POST /api/login OR /api/token ENDPOINT that exchanges email+password (or any credential) for an api_token over the API alone - token acquisition today is entirely a side-effect of a full Laravel session-cookie web login via app/Http/Controllers/Auth/LoginController.php (uses Illuminate AuthenticatesUsers trait, CSRF-protected, session guard 'web').
- For a fully decoupled Nuxt SPA (no Blade session), this is the single biggest structural gap: a proper stateless auth endpoint (e.g. POST /api/v2/auth/login returning {api_token,user}, plus logout/invalidate, register, password reset/recover, email verification) must be built fresh - none of those flows exist as JSON API endpoints today. Current /user/reset, /user/recover, /user/register/{hash?} are Blade form-post routes in web.php returning redirects/views, in app/Http/Controllers/UserController.php (NOT the API namespace).
- Many v2 'auth:api' endpoints don't actually rely on the Laravel route middleware group; controllers instead have a private getUser() helper (duplicated verbatim in GroupController, EventController, DeviceController, AlertController) that tries Auth::user() (session) first, falling back to auth('api')->user() (token) - explicitly to make PHPUnit feature tests (which use session auth) and real API-token clients both work through the same code path. This means some v2 'create/update/delete' routes are NOT wrapped in Route::middleware('auth:api') in routes/api.php at all (e.g. groups POST/PATCH, events POST/PATCH, devices POST/PATCH/DELETE, alerts PUT/PATCH) - they rely entirely on the controller-level getUser() throwing AuthenticationException if neither guard resolves a user. Only a subset is wrapped with explicit auth:api middleware in api.php: /events/{id}/volunteers (list/add), /usersgroups/*, groups/{id}/volunteers PATCH+DELETE, networks/{id}/tags POST+PUT+DELETE, /moderate/*.
- api_token is passed by existing JS/PHPUnit clients as a query string parameter ?api_token=xxx (confirmed in tests/Feature/Groups/APIv2GroupTest.php) - not as an Authorization header, though TokenGuard supports both.
- OpenAPI: package darkaonline/l5-swagger ^8.3 is installed. ALL and ONLY the /api/v2/* endpoints carry @OA annotations (in the API/*.php controllers and in app/Http/Resources/*.php for schema definitions e.g. Group, GroupSummary, Party, PartySummary, Device, Network, NetworkSummary, Tag, Alert, Item, Volunteer). The entire legacy/unversioned block in routes/api.php (lines 1-70: homepage_data, party/group stats, outbound/info, users/me, users, users/changes, networks/{id}/stats, groups/, groups/changes, groups/network/, events/network/*, events/{id}/volunteers, usersgroups/*, devices/{page}/{size}, users/{id}/notifications, talk/topics, timezones) has ZERO OpenAPI annotations. The Info/SecurityScheme block lives at the top of app/Http/Controllers/ApiController.php.
- Test coverage: v2 endpoints are well covered - tests/Feature/Groups/APIv2GroupTest.php, GroupSummaryApiTest.php, GroupTagsTest.php; tests/Feature/Events/APIv2EventTest.php; tests/Feature/Devices/APIv2DeviceTest.php; tests/Feature/Networks/APIv2NetworkTest.php, NetworkStatsTest.php; tests/Feature/Alerts/AlertsTest.php; tests/Unit/Device/DeviceItemTypesTest.php (Items). Legacy v1 endpoints have thinner but present coverage: tests/Feature/Zapier/ZapierNetworkTests.php (changes endpoints), tests/Feature/Fixometer/DeviceApiQueryTest.php (getDevices), tests/Feature/Stats/*Test.php (party/group/network stats helpers, but not necessarily the raw HTTP routes), tests/Integration/*.test.js (JS/vitest integration tests for group/event/device/grouptags touching the API from the client side). No dedicated test files found for: /api/homepage_data route itself, /api/outbound/info, /api/talk/topics, /api/timezones, /api/users/{id}/notifications as standalone route tests (though underlying services may be unit tested elsewhere).
- Response envelope inconsistency: most v2 GET-list endpoints wrap payload in {"data": [...]} (groups/summary, groups/names, groups/tags, items, alerts) via Laravel API Resource collections, but some v2 endpoints return bare arrays/collections without the data wrapper (getEventsForGroupv2 returns PartySummaryCollection directly, moderateEventsv2 wraps in response()->json($ret) without data key, getNetworkGroupsv2/getNetworkEventsv2 return bare Resource collections). A Nuxt client's API layer needs to handle this per-endpoint inconsistency (Freegle's iznik-nuxt3 API wrapper pattern should not assume a single envelope shape).
- routes/web.php (479 lines, ~167 routes) is where ALL of the following live ONLY as Blade-rendering / session-authenticated / redirect-returning controllers, with no JSON API equivalent: user registration (/user/register/{hash?}), password reset/recover (/user/reset, /user/recover), profile view/edit (/profile/*: edit-info, edit-password, edit-language, edit-preferences, edit-tags, edit-photo, edit-admin-settings, edit-repair-directory), user admin list/search/soft-delete (/user/all, /user/all/search, /user/soft-delete), notifications mark-as-read (/markAsRead/{id?}), dashboard + host dashboard (/dashboard, /dashboard/host), device search/upload/delete-image (/device/search, /device/image-upload/{id}, /device/image/delete/*), group create/edit/join/invite/image-upload (/group/create, /group/edit/{id}, /group/join/{id}, /group/invite, /group/accept-invite, /group/image-upload/{id}), event/party create/edit/join/invite/RSVP-remove/update-quantity/image-upload (/party/create, /party/edit/{id}, /party/join/{id}, /party/invite, /party/remove-volunteer, /party/update-quantity, /party/update-volunteerquantity, /party/image-upload/{id}), admin stats (/admin/stats, /admin/stats/1, /admin/stats/2), category/brands/skills/tags CRUD (/category, /brands, /skills, /tags), maps proxy for Google Places (/maps/autocomplete, /maps/place-details - deliberately server-side to hide API key), calendar feeds (/calendar/user|group|network|group-area/{...} - iCal, not JSON), CSV export (/export/devices, /export/devices/event/{id}, /export/devices/group/{id}, /export/groups/{id}/events, /export/networks/{id}/events), style guide (/style/*), preview-deploy admin tool.
- Group JOIN has no API endpoint at all (only /api/usersgroups/{id} DELETE for leave exists); joining a group is Blade-only via GET /group/join/{id} in app/Http/Controllers/GroupController.php (not API namespace), which presumably creates a UserGroups row directly from a GET request (no CSRF-safe POST, no JSON response) - would need a proper POST /api/v2/groups/{id}/join or /api/v2/usersgroups equivalent.
- Event RSVP/attendance from the ATTENDEE side (join an event as opposed to add-a-volunteer-as-host) has no v2 API: /party/join/{id} is Blade-only (PartyController::getJoinEvent). The only event-people API endpoints are host-facing: GET/PUT /api/events/{id}/volunteers (v1, auth:api) for listing/adding volunteers by a host, with no v2 equivalent and no self-service RSVP or 'my attendance status' endpoint.
- Image/file uploads have NO API endpoints anywhere - all upload actions (group image, event/party image, device photo, profile photo) are Blade POST routes in web.php calling FixometerFile::upload() directly against $_FILES, e.g. /group/image-upload/{id}, /party/image-upload/{id}, /device/image-upload/{id}, /profile/edit-photo. The v2 create/update Group/Event/Device endpoints DO accept an 'image'/'file' multipart field internally (reusing the same FixometerFile helper) but there's no standalone 'upload a photo and get back a URL/ref to attach later' endpoint - relevant for a Capacitor mobile app which will want to pick/capture a photo independent of the parent record's save.
- Search: no dedicated search API exists. Device search is folded into GET /api/devices/{page}/{size} query params (v1, no v2 equivalent). Group/event/user text search only exists Blade-side (/user/all/search, /device/search) with no JSON contract.
- Talk/Discourse: only one read endpoint (GET /api/talk/topics/{tag?}) proxying DiscourseService::getDiscussionTopics. No endpoints to fetch a single topic's posts, post a reply, mark discourse notifications read, or SSO-login into Discourse over the API — those flows exist server-side via app/Services/DiscourseService.php and Blade-triggered SSO redirect but aren't exposed as JSON.
- Admin areas (AdminController stats, PreviewDeployController, RoleController, BrandsController, SkillsController, CategoryController, GroupTagsController CRUD (Blade CRUD is separate from the v2 network-tags API which only covers per-network tags)) are 100% Blade-only, no API surface.
- Dashboard/home aggregate data for a logged-in user (app/Http/Controllers/DashboardController.php: index() and getHostDash()) is Blade-only - no JSON endpoint returns 'my dashboard' data (my groups, my upcoming events, my host stats) in one call; a Nuxt dashboard would need this composed client-side from multiple v2 calls or a new endpoint.
- User preferences (notification opt-in/out flags used by Fixometer::usersWhoHavePreference()) are edited only via Blade POST /profile/edit-preferences; no API read/write.
- GroupController::listTagsv2 and GroupController's own dual-auth getUser() differ subtly: listTagsv2 treats 'not authenticated' as a valid state returning empty data (soft-fail), whereas createGroupv2/updateGroupv2/etc throw AuthenticationException via getUser(). A unified Nuxt-side auth-required vs auth-optional endpoint convention should be decided.
- api/v2/networks/{id}/stats and api/v2/networks/{id}/tags have NO auth/permission check in code despite being under a network resource, while the v1 /api/networks/{network}/stats/ DOES enforce Auth::user()->can('view',$network) policy - an inconsistency worth resolving/documenting when porting.
- AlertController::updateAlertv2 calls \Cache::clear('alerts') at line 225 - Illuminate's Cache facade has no clear($key) method (only forget($key) or flush()); this looks like a latent bug (cache not actually invalidated on alert edit) worth flagging to the target team, not something to replicate in the new API design.

## Risks
- Building the Nuxt SPA against the current TokenGuard means storing api_token client-side (localStorage/cookie) indefinitely - it's a non-expiring, non-rotating credential (Str::random(60) generated once, reused forever, only regenerated if the column is ever nulled). For a public SPA + future Capacitor app this is weaker than Sanctum's per-device revocable tokens; consider whether to introduce Sanctum during the migration rather than carry the legacy scheme forward.
- No logout/revoke-token endpoint exists - a stolen api_token cannot be invalidated via API today (would need direct DB access or a Blade-authenticated flow to force User::ensureAPIToken() regeneration, and even that method only generates if empty, it never rotates an existing token).
- The dual Auth::user()-then-auth('api')->user() fallback pattern in v2 controllers exists to make session-based PHPUnit tests pass without needing a token; once Laravel is API-only, this session branch becomes dead weight/confusing but must stay if PHPUnit tests keep using $this->actingAs(). Worth deciding whether backend tests should switch to token-based auth to match real SPA behavior (better fidelity) as part of the migration.
- api_token transmitted as a URL query parameter (?api_token=) is a real risk (logged in server/proxy access logs, browser history, Referer headers) - a Nuxt client should prefer Authorization: Bearer, and this should be enforced/deprecated server-side during the rewrite.
- GET /api/groups/ (v1, getGroupList) returns raw Eloquent rows with NO field hiding, unlike the careful hiding in getUserInfo - if $hidden on the Group model doesn't already exclude sensitive columns (e.g. shareable_code, wordpress_post_id), this endpoint over-exposes data; verify App\Group::$hidden before relying on it, or better, deprecate it in favor of /v2/groups/summary.
- GET /api/users (v1, getUserList, admin-only) returns raw User rows without makeHidden() calls (unlike getUserInfo which explicitly hides api_token etc.) - likely exposes every user's api_token, recovery tokens, etc. to any Administrator caller who has the URL; must not be ported as-is into the new API without adding hiding/resourcing.
- routes/api.php's v1 groups/network/ and events/network/* endpoints join on users.api_token for matching 'the current network user' — a brittle pattern (equality-join on a secret token) that should not be replicated in new endpoint design.
- Heavy nested response shapes (getGroupsByUsersNetworks, getEventsByUsersNetworks) compute per-item stats and nested collections inline with N+1-prone loops (foreach group -> getGroupStats(), foreach party -> getEventStats()) — these are the closest existing analogs for 'my dashboard' data but are not efficient enough to be the basis of a new high-traffic SPA dashboard endpoint; a fresh, batched implementation is warranted (note GroupController::listSummaryv2 and its ids= param already demonstrate the better batched pattern to follow).

## Recommendations
- Auth: build a proper stateless auth family under /api/v2/auth (or /v2/session): POST /login (email+password -> {api_token or JWT, user}), POST /logout (revoke), POST /register, POST /password/forgot, POST /password/reset, GET /email/verify/{id}/{hash}, POST /email/resend. Strongly consider migrating from Laravel TokenGuard to laravel/sanctum (used by the Freegle iznik-nuxt3 reference stack conventions of short-lived/rotatable tokens) rather than porting the api_token-forever model; keep the Capacitor app in mind (sanctum personal access tokens work well for native/mobile too).
- User profile/account family: GET/PATCH /api/v2/users/me (self profile, distinct from admin /users list), PATCH /api/v2/users/me/password, PATCH /api/v2/users/me/preferences, PATCH /api/v2/users/me/language, POST /api/v2/users/me/photo, PATCH /api/v2/users/me/tags (skills), soft-delete/close-account endpoint, admin user list+search+edit+role-assignment endpoints (currently /user/all, /user/all/search, /user/edit/{id} Blade-only) and GET /api/v2/users/{id} public-ish profile view (currently /profile/{id} Blade).
- Group membership family: POST /api/v2/groups/{id}/join (self-join, replaces Blade GET /group/join/{id}), keep existing DELETE /api/usersgroups/{id} but port/alias it under /api/v2/groups/{id}/leave or /api/v2/usersgroups/{id} for naming consistency with the rest of v2; POST /api/v2/groups/{id}/invite + accept-invite endpoints (currently Blade postSendInvite/confirmInvite/confirmCodeInvite).
- Event attendance family (attendee-facing, currently absent from v2 entirely): POST /api/v2/events/{id}/rsvp (self join, replaces Blade /party/join/{id}), DELETE /api/v2/events/{id}/rsvp or reuse pattern of remove-volunteer, GET /api/v2/events/{id}/my-status; keep and version the existing host-facing list/add-volunteer endpoints as /api/v2/events/{id}/volunteers GET/PUT/DELETE (individual volunteer), and add PATCH for updating a volunteer's quantity/role (currently Blade /party/update-volunteerquantity, /party/remove-volunteer).
- Event/Group DELETE: no v2 delete endpoints exist for events or groups at all (only Blade /party/delete/{id}, /group/delete/{id}) - add DELETE /api/v2/events/{id} and DELETE /api/v2/groups/{id} (or archive-only pattern matching existing archived_at field on groups; decide if events get an equivalent soft-cancel vs hard delete).
- Uploads: add a generic-ish media endpoint family, e.g. POST /api/v2/uploads (multipart, returns a draft ref usable by the existing 'draft id' pattern already present in DeviceController::createDevicev2 which copies pre-uploaded photos by draft id) so photo capture in a Capacitor app can happen independently of saving the parent group/event/device record; also DELETE /api/v2/uploads/{id} and per-entity photo-delete endpoints (currently Blade GET routes(!) at /group/image/delete/*, /party/image/delete/*, /device/image/delete/* - note these are unsafe GET-based deletes today, a good opportunity to fix to DELETE verbs in the new API).
- Dashboard/home: add a single GET /api/v2/dashboard (or compose client-side from summary endpoints) returning the logged-in user's groups, upcoming events they host/attend, and pending moderation counts, replacing DashboardController::index()/getHostDash(). Given listSummaryv2's ids= batching pattern already proven, prefer several small parallel-fetchable v2 endpoints over one monolithic blob for SPA cache-friendliness (matches Freegle's per-store Pinia module pattern).
- Search: add GET /api/v2/devices (paginated, replaces v1 /api/devices/{page}/{size} with proper query-string pagination, OpenAPI docs, and a Device summary Resource) and a text search endpoint for groups/events/users if the SPA needs a global search box (none exists today even in Blade for global cross-entity search).
- Admin CRUD family entirely missing from API: categories, brands, skills, group-tags (global, distinct from per-network tags already in v2), roles, alerts (mostly covered), admin stats. Port app/Http/Controllers/{CategoryController,BrandsController,SkillsController,GroupTagsController,RoleController,AdminController} to /api/v2/admin/* with Administrator-only auth.
- Talk/Discourse: expand beyond topic-list read: add endpoints (likely still server-proxied for SSO secrecy) for fetching a topic's posts/replies, posting a reply, and marking discourse notifications read, since Discourse SSO secrets must stay server-side - the Laravel API becomes the necessary proxy layer here, not something the SPA can call directly.
- Maps: keep /maps/autocomplete and /maps/place-details server-proxied (already correctly done to hide the Google API key) but port them under /api/v2/maps/* with auth:api instead of session, since the SPA's group/event location pickers need this and currently only work inside an authenticated Blade session.
- Export/calendar feeds (CSV export, iCal calendar subscriptions) can likely stay as direct-download Laravel routes (not JSON, consumed by external calendar apps / browser downloads) rather than being reimplemented as SPA-fetched JSON - flag as 'keep as Laravel passthrough links' rather than API endpoints, but confirm CORS/auth still works when linked from the Nuxt app.
- Standardize the v2 response envelope: audit and make every v2 list endpoint consistently return {data: [...]} (some currently don't - see getEventsForGroupv2, getNetworkGroupsv2, getNetworkEventsv2, moderateEventsv2/moderateGroupsv2) before or during the port, so the Nuxt API client layer can have one unwrap function instead of per-endpoint special-casing.
- Add OpenAPI annotations for every currently-unannotated legacy endpoint being carried into v2 equivalents (homepage_data/stats aggregates, timezones, notifications, talk/topics) so the new API has full l5-swagger coverage before client codegen/typing in Nuxt.
- Given Zapier and RepairTogether and TRP.org depend on several v1 endpoints (party/group stats, outbound/info, groups/changes, users/changes, usersgroups/changes, networks/{id}/stats, groups/network/, events/network/*), these MUST be preserved with stable contracts even as Laravel becomes API-only - do not remove them when building v2 equivalents for the new SPA; treat them as a separate 'external integrations' surface with its own versioning discipline.
