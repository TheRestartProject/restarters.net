# Findings: vue-prs

## Summary
Five open PRs (863, 866, 867, 868, 892) collectively add ~20 new/extended /api/v2 endpoints across brands, categories, group-tags, roles, skills, users-list, user-profile (5 tabs incl. tus/uppy resumable photo upload), and group-view permission flags. All target `develop`, all CI-green, no detected git conflicts, but GitHub's own mergeable computation was UNKNOWN and all branches are 22 commits behind current develop tip. The Vue 2.7/Blade-mount frontend work in every PR should be discarded/reimplemented in Nuxt 4 (Vue3/Pinia/bootstrap-vue-next); the Laravel API controllers, Http Resources, routes/api.php additions, and PHPUnit Feature tests are the valuable, portable payload and should be cherry-picked (868's tus-php/Uppy upload subsystem is the most complex and highest-value piece to preserve exactly).

## Key facts
- All 5 PRs target base branch develop; all have CI green (SonarCloud + CircleCI pass) as of check time; gh reports mergeable/mergeStateStatus as UNKNOWN (GitHub hasn't computed it, likely needs a re-check) but `git merge-tree` against origin/develop shows no textual conflicts for any of the 5 branches.
- Commits-ahead-of-develop (git rev-list --count develop...branch): 863=23, 866=6, 867=4, 868=18, 892=1. All are 22 commits behind current develop tip, i.e. none are rebased onto the very latest develop.
- Local worktrees confirmed present under .worktrees/: refdata-vue (863), users-vue (866), cantcreate-vue (867), profile-vue (868), groupview-vue (892) — plus unrelated worktrees i18n-widgets, issue-853, map-groups, maps-proxy, res-2062, rm-outbound.
- Common pattern across all PRs: Vue 2.7 components registered by string key in resources/js/app.js's component map (e.g. 'grouppage': GroupPage, 'cantcreateeventpage': CantCreateEventPage) and mounted into Blade via a div with matching lowercase tag/class ('vue-placeholder' loading state + '.vue' wrapper div containing the component tag) — this mount convention needs a Nuxt-4 equivalent (route-per-page instead of Blade-embedded islands).
- All new endpoints follow a consistent 'v2' method-naming and URL-prefix convention already established: /api/v2/{resource} with public-safe GET and auth:api-gated mutations, using Laravel API Resources (App\Http\Resources\*) with OpenAPI (@OA) annotations for docs/schema generation — worth mining for OpenAPI-driven client codegen in the Nuxt app.
- PR 863 additionally removes legacy Blade CRUD routes (POST /brands/create, /brands/edit/{id}, /brands/delete/{id}, equivalents for skills/tags/roles/categories) replacing them with a single GET index route that pre-opens an edit modal client-side via an {editId} param — this URL-shape (index route + editId query/path param opens modal) is a UX pattern to replicate in Nuxt routing.
- PR 868 introduces genuinely new backend capability (tus resumable-upload protocol server via ankitpokhrel/tus-php, deliberately unauthenticated route because Laravel's 'api' middleware group has no CSRF) — this is infra, not just a Vue port; must be preserved and ported carefully, including the FileStore cache-key-prefix gotcha noted in code comments ('tus:server:' prefix).
- PR 892 is the only PR that modifies an EXISTING v2 endpoint's response shape (adds `permissions` object to GET /api/v2/groups/{id}) rather than adding new routes — Group.php Resource class already existed pre-PR from earlier work.
- No PR's diff touches app/Http/Controllers/API/GroupController.php except 892, meaning GET /api/v2/groups/{id} base endpoint (getGroupv2) predates these 5 PRs and lives on develop already.

## Risks
- gh reports mergeStateStatus=UNKNOWN for all 5 PRs (GitHub's own merge-conflict computation hadn't run/cached) — before folding in, re-run `gh pr view N --json mergeable,mergeStateStatus` or attempt an actual local merge to get GitHub's authoritative answer; the git merge-tree spot-check here is a reasonable proxy but not identical to GitHub's algorithm.
- All 5 branches are 22 commits behind current develop tip — rebasing/cherry-picking the API commits onto the new Nuxt-era Laravel API-only branch will likely need manual conflict resolution against whatever landed in those 22 develop commits (not sampled here).
- PR 863 and 868 remove/gut Blade view files and legacy POST routes; if the fold-in strategy is 'cherry-pick API commits only' without the Blade route changes, care is needed not to accidentally reintroduce or leave orphaned legacy routes/views inconsistent with the API-only target architecture.
- PR 868's tus/uppy upload flow is the most architecturally significant piece (new protocol, new controller, new helper, unauthenticated route) — reimplementing rather than porting risks losing subtle correctness fixes documented in code comments (Request::createFromGlobals eager-construction avoidance, cache key prefix).
- None of these PRs' Vue 2 components should be kept as-is per task framing — they are Options-API Vue 2.7 + presumably bootstrap-vue; all must be rewritten in Vue 3 Composition-API/Pinia/bootstrap-vue-next conventions matching the Freegle iznik-nuxt3 patterns, so effort estimate should treat 'Vue pages/components' as throwaway design references only, never as portable code.
- AdminCrudPage.vue in PR 863 is a shared generic component reused by 5 pages — worth studying its prop/slot API as a spec for a Nuxt equivalent generic admin-CRUD composable/component, but not for direct porting.
