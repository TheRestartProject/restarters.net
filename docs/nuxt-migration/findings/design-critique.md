## BLOCKING FLAWS (2)

### 1. The 'auth-web' session route group's CSRF posture is unspecified, and the natural implementation (reusing Laravel's existing 'web' middleware group to get StartSession) will 419 the primary login/register/logout endpoints.
EVIDENCE: app/Http/Kernel.php 'web' group = EncryptCookies, StartSession, CheckForRepairNetwork, LanguageSwitcher, AddQueuedCookiesToResponse, ShareErrorsFromSession, VerifyCsrfToken, SubstituteBindings, LogHTTPErrorsToSentry, YesterdayBanner. app/Http/Middleware/VerifyCsrfToken.php has an empty $except array — no existing exclusion pattern to copy. design.md §4.2/§4.3 only says the new auth endpoints run in 'a route group with session middleware (StartSession/cookies, no Blade)' and never mentions CSRF at all; plans/active/nuxt-migration.md line 18 (task A4) likewise says 'session middleware group' with no CSRF exclusion noted. Since StartSession/AddQueuedCookiesToResponse/EncryptCookies are only ever bundled together with VerifyCsrfToken in this codebase's Kernel (there is no pre-existing 'session-but-no-csrf' group to reuse), an implementer following Laravel/this-codebase's own convention (Route::middleware('web')) will pull in VerifyCsrfToken, and a cross-origin POST /api/v2/auth/login fetch from the Nuxt SPA carries no CSRF token (design explicitly commits to header-token/no-credentialed-CORS in §3, so there is no XSRF cookie/token exchange mechanism described anywhere in the doc), producing a 419 TokenMismatchException that breaks login/register/logout outright. This is exactly the failure mode findings/docker-ci.md and findings/critique.md flag as an open question — design.md never closes it.
FIX: Explicitly define 'auth-web' in design.md as StartSession + AddQueuedCookiesToResponse + EncryptCookies with VerifyCsrfToken explicitly excluded (documenting why: Bearer-token auth is not ambient-credential auth, so CSRF protection is inapplicable to these endpoints), and add a phpunit test asserting POST /api/v2/auth/login succeeds without a CSRF token from a cross-origin-style request.

### 2. The shareable group/event invite-code flow (an actively shipping feature) depends on PHP session continuity across an anonymous page visit and a later authenticated page load, and is not addressed anywhere in the design's auth/API sections — it will silently stop working for existing users.
EVIDENCE: app/Group.php:382-386 defines getShareableLinkAttribute() (in $appends, so serialized on virtually every Group API response) returning url("group/invite/{$this->shareable_code}"); the identical pattern exists for Party (PartyController::confirmCodeInvite). This link is rendered in a real, live UI: resources/views/includes/modals/group-invite-to.blade.php and event-invite-to.blade.php show a 'shareable_link_box' input pre-filled with $group->shareable_link / $event->shareable_link under the label groups.shareable_link / events.shareable_link, with an explanatory groups.type_shareable_link_message string — this is the 'invite anyone with this link' feature, not dead code. Route GET /group/invite/{code} -> GroupController::confirmCodeInvite (routes/web.php:426, wrapped only in 'ensureAPIToken', i.e. guest-reachable) creates a new Invite row and does session()->push('groups.'.$code, $hash) (GroupController.php:678), then redirects to /user/register. The actual acceptance happens later via App\Http\Middleware\AcceptUserInvites (attached only to the /dashboard route, routes/web.php:316), which reads session()->get('groups')/'events' and applies pending invites on the next authenticated page load — this is a genuinely different, session-bridging mechanism from the already-stateless /group/accept-invite/{id}/{hash} (GroupController::confirmInvite, status-hash-on-UserGroups pattern) that design.md §5 explicitly names as a kept 'emailed deep-link'. design.md's stateless-invite-hash coverage is scoped only to POST /api/v2/auth/register's optional invite_hash field (§4.2) — nothing in §4, §5, or plans/active/nuxt-migration.md (grepped for 'invite'/'shareable'/'bridge': only group-accept-invite and the register-time invite_hash appear, e.g. plan line 36 'invite-accept email deep-link redirector kept') covers /group/invite/{code} or /party/invite/{code} at all. An SPA with ssr:false and no general Laravel session for logged-in page views has no server-side session to bridge 'visited invite link as guest' -> 'logged in as an existing user' -> 'apply pending invite on /dashboard load'; the login endpoint spec in §4.2 (POST /api/v2/auth/login {email,password}) has no invite_hash field either. Result: an existing user who clicks a shared group/event invite link and logs in (rather than registering) will never be added to the group/event, with no error surfaced to them or the host who shared the link — a silent regression of a currently-working feature.
FIX: Either (a) redesign /group/invite/{code} and /party/invite/{code} to resolve and apply the Invite directly and statelessly against Auth::user() if already logged in (mirroring the already-stateless confirmInvite pattern), and to pass the code through the URL query string into both the register AND the new login endpoint (adding an optional invite_code/invite_hash field to POST /api/v2/auth/login, not just /register) so an existing user's login also completes the pending invite in one round trip; or (b) explicitly scope this flow out of the migration and document the resulting UX change (host-shared invite links stop working for already-registered recipients) as a deliberate, called-out product decision rather than an accidental drop.

## WEAKNESSES (3)
- design.md §4.2 says POST /api/v2/auth/login fires the Login event 'so Wiki/Discourse listeners run', but this is doubly questionable: (1) it is factually imprecise — grepping app/Providers/EventServiceProvider.php shows only LogSuccessfulLogin (+ conditional LogInToWiki) are wired to the Login event; there is no Discourse listener on Login at all (spinen's own LogoutDiscourseUser fires only on Logout), so 'Discourse listeners run' on login is simply not true. - Deleting AddCorsHeaders and moving to Laravel's HandleCors does NOT break same-origin legacy Blade->/api calls (resources/js/mixins/auth.js, resources/js/bootstrap.js): CORS response headers are a browser-enforced check that only applies to cross-origin requests, so same-origin Vue2-island XHR/fetch calls from Blade pages served at the same nginx origin as /api are unaffected regardless of what Access-Control-* headers are or aren't present.
- The auth:sanctum,api dual-guard fallback for legacy Bearer api_token consumers is technically sound: Laravel's multi-guard Authenticate middleware tries each guard in order; Sanctum's PersonalAccessToken::findToken() returns null for tokens that don't match its 'id|plaintext' or sha256-hashed formats (confirmed no column-naming collision between Sanctum's personal_access_tokens table/tokens() relation and the existing users.api_token column used by the 'api' TokenGuard in config/auth.php), so it correctly falls through to the legacy 'api' guard for old-style tokens.
- The SSO-bridge design correctly anticipates and works around the cross-origin cookie problem: because config/cors.php sets supports_credentials=false and the Nuxt client's $fetch calls aren't expected to use credentials:'include', a cross-origin XHR login's Set-Cookie response header would be silently dropped by the browser — the design explicitly does NOT rely on that cookie, instead using a short-lived signed ticket consumed during a top-level (non-XHR) navigation to /auth/bridge, where a real first-party session/cookie can be established normally.
- F2's vite.config.js trimming to keep only resources/global/{js,css} and resources/wiki/{js,css} entries while dropping resources/js/app.js and resources/sass/app.scss is directionally correct and matches the current file's entry list (aside from the one cross-import flaw noted above).
