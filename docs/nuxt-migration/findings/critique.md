## Contradictions between readers
- Auth transport mechanism: auth-integrations recommends Sanctum SPA STATEFUL COOKIE auth as primary (to preserve Discourse SSO and MediaWiki cookie-sharing integrations with minimal redesign), explicitly proposing SESSION_DOMAIN=.restarters.net shared across app/api/wiki/talk subdomains. But api-surface, docker-ci, and i18n-globals all independently recommend BEARER/TOKEN auth as primary, citing Capacitor incompatibility with cookies, CORS simplicity, and the query-string-token security smell; freegle-stack shows Freegle's actual precedent is localStorage-only dual-header JWT+persistent-token, explicitly NOT cookies, specifically to avoid SSR-hydration cross-user leakage. These are not both 'primary' — the design doc must pick one as primary and treat the other as a compatibility bridge (auth-integrations itself proposes a hybrid but frames cookies as primary/token as secondary-for-mobile, inverse of the other three readers' framing).
- CORS/origin topology: docker-ci's concrete dev-environment recommendation has the browser hit Nuxt directly on its own port (:3000) calling Laravel's API on a different port (:8001/api) with CORS enabled — i.e. deliberately cross-origin. auth-integrations recommends the opposite: 'keep app+api same-origin (reverse-proxied)... the simplest and most Safari/Chrome-ITP-resilient option... likely how Discourse/MediaWiki cookie sharing already works.' If cookie-based Sanctum auth is chosen, docker-ci's cross-origin dev topology directly undermines auth-integrations' cookie strategy (third-party-cookie blocking in Safari/Chrome ITP) and the two readers' recommendations cannot both be followed as stated.
- Admin-CRUD and user-list and profile-edit 'missing API surface': api-surface's KEY FACTS state GroupTagsController CRUD, BrandsController, SkillsController, RoleController, CategoryController and admin user list/search (/user/all, /user/all/search) are '100% Blade-only, no API surface' on the current codebase, and its RECOMMENDATIONS propose designing fresh /api/v2/admin/* endpoints for all of them from scratch. vue-prs shows this is already ~built (not yet merged): PR 863 adds v2 endpoints for exactly brands/categories/group-tags/roles/skills, PR 866 adds GET /api/v2/users (listUsersv2), PR 868 adds a full profile-edit + photo-upload v2 API. Both readers are factually correct about their respective inputs (develop branch vs. open PR branches) but the design doc must not treat api-surface's 'design these from scratch' recommendation as the live plan — it should reconcile by treating vue-prs's cherry-pick list as the primary path for these five feature areas and only fall back to api-surface's from-scratch endpoint shapes where a PR's design is rejected or its branch fails the 22-commits-behind rebase.
- Upload/media endpoint design: api-surface's RECOMMENDATIONS independently propose a new generic 'POST /api/v2/uploads (multipart, returns a draft ref...)' family for all entity photo uploads. vue-prs reports PR 868 already implements a resumable tus-php + Uppy-based upload subsystem (flagged as 'the most complex and highest-value piece to preserve exactly') for profile photos specifically. These are two different upload architectures (simple multipart-POST-returns-URL vs. resumable tus protocol) proposed for overlapping problem space by readers working from different evidence; the design doc must pick one canonical upload mechanism, and if tus/Uppy is chosen (recommended, since it already exists and is CI-green) then api-surface's generic-uploads proposal should be superseded/merged into it rather than run in parallel for other entities (group/event/device images).

## Design decisions needed
- Auth transport & token lifecycle: Sanctum SPA stateful-cookie vs. Sanctum/custom Bearer token vs. hybrid-with-one-primary. Options and evidence: (a) Sanctum cookie — preserves Discourse SSO (spinen/laravel-discourse-sso, session+auth guard, browser-redirect handshake) and MediaWiki silent-login (Cookie::queue() on the Laravel response, requires shared parent domain) with near-zero redesign per auth-integrations, but requires same-parent-domain topology, breaks under 'Access-Control-Allow-Origin: *' (current AddCorsHeaders middleware), and does not extend to a cookie-less Capacitor WebView. (b) Bearer/token (Sanctum PAT) — matches Freegle's actual shipped precedent (localStorage JWT+persistent-token dual header, freegle-stack), avoids CORS/ITP cookie issues (api-surface, docker-ci), is Capacitor-ready by construction, but requires a bespoke bridge for the Discourse SSO redirect handshake and MediaWiki cookie-sharing (auth-integrations RISKS: 'forces either (a) Sanctum SPA stateful-cookie... or (b) a bespoke bridge'). Must also decide fate of the existing non-expiring 'restarters_apitoken'/TokenGuard mechanism (retire per auth-integrations) and whether backend PHPUnit tests switch from session-based actingAs() to token-based auth to match real SPA behavior (api-surface RISKS).
- Domain/CORS topology for prod and dev: same-origin reverse-proxy (app+api+wiki+talk behind one host, cookies trivially shared) vs. separate subdomains with explicit CORS (config/cors.php rewrite + retire custom AddCorsHeaders). Evidence: auth-integrations favors same-origin as 'simplest and most Safari/Chrome-ITP-resilient'; docker-ci's concrete dev-service plan (nuxt on :3000 calling Laravel on :8001/api) is cross-origin by default; current AddCorsHeaders hardcodes Access-Control-Allow-Origin:'*' which is incompatible with credentialed requests either way and must be explicitly retired regardless of which topology is chosen. This decision is entangled with the auth-transport decision above and with adv-fly's unresolved production Fly-app topology (single image vs. two Fly apps/static asset serving, flagged by docker-ci as explicitly out of scope for it).
- Repo/monorepo structure: new Nuxt app as a new top-level directory in this same repo vs. a wholly separate git repository (mirroring FreegleDockerWSL's separate iznik-nuxt3 repo pattern). Evidence: docker-ci's compose-service recommendation explicitly could not resolve this ('./restarters-nuxt (or wherever the new repo/dir lives)'); it determines CI job/workspace design (single checkout vs. cross-repo triggering), Taskfile task placement, and whether CLAUDE.md/.claude config needs duplicating.
- SSR vs. pure SPA (ssr:false) for the Nuxt app, and specifically whether public-facing pages need it. Options: pure SPA everywhere (simplest, matches task framing, avoids bootstrap-vue-next's lack of SSR support per styles/freegle-stack) vs. Freegle's hybrid per-route ssr:false-by-default-except-static-pages pattern. Evidence bearing on this: routes-pages found several genuinely public, currently server-rendered pages with external consumers — GroupController@view (group.show), PartyController@view (public event page), landing page, plus OutboundController's iframe/JSON branches and the /group/stats,/party/stats/wide widget endpoints embedded on therestartproject.org/partners. No reader determined whether Google indexing or partner-iframe embedding of these specific pages requires crawlable server-rendered HTML (as opposed to the iframe/stats endpoints which already stay server-side regardless per multiple readers' recommendations to keep OutboundController/stats widgets resident in Laravel). freegle-stack explicitly flags this exact open question ('unless SEO for public group/event pages is a stated requirement') without resolving it.
- newToOld() adapter fate in the Vuex→Pinia port: keep a compatibility-adapter layer in new Pinia stores so ~40+ mixin-dependent components (mixins/event.js, mixins/group.js field names like idevents/idgroups/venue) need zero renaming, vs. do a coordinated one-time rename pass to the actual /api/v2 field names during the port. Evidence: vue-components' RISKS/RECOMMENDATIONS lay out both options explicitly as (a) lower-risk-shim vs (b) cleaner-larger-diff, with no reader recommending one over the other decisively — must be chosen given it affects nearly every ported component.
- Cherry-pick-vs-redesign for the 5 open-PR feature areas (admin CRUD in PR 863, user list in PR 866, profile+tus-upload in PR 868, group permissions in PR 892) versus api-surface's independently-proposed fresh endpoint designs for the same feature areas. Evidence: see contradictions above — vue-prs's PRs are CI-green, already exist, and PR 868 in particular encodes non-obvious correctness fixes (tus cache-key-prefix, PII hiding) that a from-scratch redesign risks losing; but all 5 branches are 22 commits behind develop and gh reported mergeable=UNKNOWN, so there is real integration risk to weigh against the redesign-fresh option.
- Canonical upload/media architecture: adopt PR 868's tus-php (resumable, chunked) + Uppy Dashboard client pattern as the single upload mechanism for every entity photo (group, event, device, profile) vs. build the simpler generic multipart POST /api/v2/uploads endpoint api-surface proposed, used only for non-profile entities while PR 868's tus stays profile-specific (i.e., two upload mechanisms coexisting). Evidence: vue-prs calls PR 868 'the most complex and highest-value piece to preserve exactly'; api-surface's proposal was made without visibility into PR 868 (independent reader). A future Capacitor app's photo-capture-then-attach-later flow (api-surface's stated rationale for a generic uploads endpoint) needs to be satisfied by whichever mechanism is chosen.
- Auth-gating UX pattern in the Nuxt app: conventional Nuxt route middleware (definePageMeta({middleware:'auth', requiresRole:'Administrator'})) vs. Freegle's deliberate no-middleware/always-mounted-LoginModal/forceLogin-flag pattern (freegle-stack: 'no middleware/ directory exists... this is a design choice, not an incidental gap'). Evidence bearing on it: current Laravel does controller-level (not route-level) admin gating via Fixometer::hasRole()->redirect (routes-pages), which the Nuxt app must replace with SOME consistent client-side+API-enforced convention; routes-pages explicitly recommends a route-meta requiresRole pattern, which is the conventional-middleware option, not Freegle's modal pattern — the design doc must decide rather than default to copying Freegle.
- CI job topology: extend the existing single monolithic CircleCI `build` job (35min docker startup wait + 45min phpunit + jest + 10min playwright, already CI-time-constrained per docker-ci) to also run Nuxt build+vitest+playwright, vs. fan out into a parallel `build-nuxt` job requiring only task docker:up-core. Evidence: docker-ci strongly recommends the parallel-job split given the existing job's already-tight time budget; this also interacts with the repo-structure decision above (a separate repo would make this a separate CircleCI project entirely rather than a job).
- i18n library and pluralization-compatibility strategy: @nuxtjs/i18n with a custom messageResolver/pluralRules port of resources/js/mixins/lang-utils.js's translateWithLocale/choiceWithLocale (preserving Laravel's singular|plural/{n}/[n,m] syntax verbatim, i18n-globals' recommended option (a)) vs. a one-time migration of all lang/*.php strings into ICU MessageFormat for native vue-i18n/@nuxtjs/i18n pluralization (option (b), touches 3 actively-maintained locales x 27 files). Evidence: i18n-globals lays out both with a stated preference for (a) as lower-risk, but this recommendation was made citing an unverified assumption that Freegle uses @nuxtjs/i18n as precedent — a direct check of Freegle's package.json during this critique found no i18n module at all, so there is in fact no Freegle precedent to fall back on and this decision is fully novel design work, not an adaptation.
- Playwright worker parallelism: keep workers:1 (current CSRF-driven constraint, both for the legacy suite and any ported Nuxt suite) vs. parallelize once the auth-transport decision (above) removes Laravel session-CSRF from the picture. Evidence: playwright-regression and docker-ci both flag the current workers:1/session-CSRF coupling and both defer the decision to whatever auth model is chosen — this is a direct downstream consequence of the auth-transport decision, not independent, and the design doc should state it as a consequence rather than a separate open question.
- GET-as-mutation route remediation scope: convert every internal GET-mutation endpoint (markAsRead, group/delete/{id}, group/image/delete/*, party/join/{id}, party/deleteimage, party/image/delete/*, device/image/delete/*, brands/delete/{id}, skills/delete/{id}, tags/delete/{id}) to proper REST verbs in the new v2 API, vs. preserve any subset that has external dependents (emailed invite links, partner iframes) under their current GET contract. Evidence: routes-pages and api-surface both catalog these extensively; api-surface separately insists that v1 endpoints consumed externally by Zapier/TRP.org/RepairTogether must keep stable contracts — the design doc needs an explicit per-route classification (internal/safe-to-redesign vs external/must-preserve), which no reader fully completed (see missing_information re: Zapier auth mechanism).
